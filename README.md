# 创想三维 12 KiB MCU Bootloader 净室重建

本工程依据 Ender-3 V4 C23 机器上三块 MCU 的完整 Flash 备份，以及原厂 Linux 升级工具 `mcu_util`，重建出可编译的 UART Bootloader 源码。协议、关键状态机、时钟、UART 和 Flash 行为经过两侧二进制交叉核对，但不声称恢复了原厂源码，也不追求与原厂 BL 逐字节相同。

> **项目状态：逆向研究 / 预发布。** 本项目与深圳市创想三维科技股份有限公司
> 无隶属或背书关系。“Creality/创想三维”仅用于说明兼容目标。

## 支持的控制板

| 配置 | 用途 | MCU | Flash | RAM | 写入块/页 | 板卡标识 |
|---|---|---|---:|---:|---:|---|
| C23 | 主板 | GD32F303 | 256 KiB | 48 KiB | 2048 字节 | `mcu0_140_G31` |
| C13 | 喷头板 | GD32F303 | 128 KiB | 32 KiB | 2048 字节 | `noz0_110_G30` |
| C10 | 热床/调平板 | GD32E230 | 64 KiB | 8 KiB | 1024 字节 | `bed0_110_G21` |

三者的 Bootloader 均占用 `0x08000000..0x08002fff`，应用程序从 `0x08003000` 开始。链接器会阻止重建 BL 超过原厂预留的 12 KiB。

F303 Flash 后端还保留原厂的双 bank 能力：运行时读取 `0x1ffff7e0`
容量字；容量超过 512 KiB 且写入地址达到 `0x08080000` 时，自动改用 FMC
bank 1 的 KEY/STAT/CTL/ADDR 寄存器。当前 C23/C13 容量不超过 512 KiB，
因此仍只访问 bank 0；E230 不使用这套双 bank 路径。

BL 自身的 12 字节板卡/Boot 版本标识固定在 BL 偏移 `0x2f80`（绝对地址
`0x08002f80`）。它是编译 Bootloader 时由所选板型写入的只读常量，不是
首次启动生成的，也不会由普通应用升级动态修改。

## Bootloader 上电流程

1. 从 `0x08000000` 的向量表进入复位处理函数，初始化数据段和 BSS。
2. 配置系统时钟：F303 为 120 MHz、两个 APB 为 60 MHz；E230 为 72 MHz、APB 不分频。
3. 初始化 SysTick 和 GPIOA 上的两个串口：USART0 使用 PA9/PA10，USART1 使用 PA2/PA3，波特率均为 115200。
4. 同时扫描两个 UART，等待主机发送裸字节 `0x75`。
5. 若收到握手，原样返回裸字节 `0x75`，锁定收到握手的 UART，并进入命令循环；此后不会自动启动应用。
6. 若在 `CONFIG_BOOT_WAIT_MS` 内没有收到握手，则检查应用程序：
   - 应用有效：清理 SysTick 和 NVIC 状态，通过应用向量表装载 MSP 和复位入口并跳转；
   - 应用无效：留在 Bootloader 中继续等待握手，不跳转到损坏的应用。

默认握手窗口为 15000 ms。应用有效性检查不是只检查向量表，而是验证原厂元数据和整个声明长度范围的 CRC。

## 应用固件格式与有效性检查

应用基址为 `0x08003000`，关键字段均为相对于应用基址的偏移：

| 偏移 | 长度 | 含义 |
|---:|---:|---|
| `0x200` | 12 字节 | 应用版本标识，例如 `mcu0_022_000` |
| `0x20c` | 2 字节 | 小端序 CRC16 |
| `0x20e` | 4 字节 | 小端序应用长度 |

CRC 使用 CRC-16/CCITT，`poly=0x1021`、`init=0`。计算范围为应用起始位置至声明长度末尾；计算时将 `0x20c..0x211` 六个元数据字节视为零。长度必须至少覆盖这些字段，并且不能超过该 MCU 的应用 Flash 容量。容量上界检查是重建版有意增加的安全加固。

Hi/V57 系统打包在 `/usr/share/klipper/fw/F009`、`F010`、`F018` 下的
MCU `.bin` 都是从应用基址加载的纯应用镜像，不包含前面的 12 KiB BL。
文件名通常写成“BL/板卡标识-应用版本”，例如
`mcu0_140_G31-mcu0_022_000.bin`：前半用于匹配现有 BL/硬件，后半才是
该文件内偏移 `0x200` 的应用版本。

应用版本在编译期放入固定元数据段；生成 `klipper.bin` 后，主机侧封装工具
再把最终 CRC16 和文件长度写入 `0x20c..0x211`。普通 `mcu_util` 升级始终
从 MCU 地址 `0x08003000` 开始写，因此会更新应用版本、CRC 和长度，但不会
擦写 `0x08000000..0x08002fff`，BL 标识和 BL 代码都保持不变。只有使用
SWD/量产烧录器写入完整 Flash，或另行实现能够自擦写 BL 区域的程序，才会
改变 BL 版本。

## 串口协议

发现握手只有一个裸字节 `75`，不带校验。握手完成后的普通数据包格式为：

```text
数据字节... + 校验字节
校验字节 = 0xff - (所有数据字节之和的低 8 位)
```

因此，整个包所有字节之和的低 8 位应为 `0xff`。单字节命令包如下：

| 功能 | 主机发送 |
|---|---|
| 查询版本 | `00 ff` |
| 开始升级 | `01 fe` |
| 启动应用 | `02 fd` |
| 查询扇区大小 | `03 fc` |

常用状态响应也按“状态字节 + 校验字节”发送：

| 状态 | 含义 |
|---|---|
| `75` | 已接受，可以继续 |
| `20` | 全部固件写入完成 |
| `1f` | 包校验失败，或请求启动的应用无效 |
| `21` | 长度非法或 Flash 写入失败 |

### 命令 `00`：查询版本

返回 25 字节数据及一个校验字节：

```text
12 字节板卡标识 + "-" + 12 字节应用版本
```

只有应用 CRC 有效时才返回应用版本；应用无效时后 12 字节填零。

### 命令 `03`：查询写入块大小

返回一个扇区代码及校验字节。F303 返回 `2`，代表 2048 字节；E230 返回 `1`，代表 1024 字节。原厂主机据此决定每次从固件文件读取多少数据。

### 命令 `01`：升级应用

升级状态机如下：

1. BL 返回 `75`，表示进入升级模式。
2. 主机发送四字节小端序固件长度和校验字节。
3. 长度包校验失败时返回 `1f`，最多接收五次；长度越界则返回 `21` 并结束本轮升级。
4. 长度有效时返回 `75`，主机开始逐块发送固件。
5. 每块先验证传输校验，再执行整页读取、合并、擦除、编程和回读验证。
6. Flash 写入失败时，BL 使用同一份 RAM 数据最多重试三次，不要求主机重发该块。
7. 非最后一块写入成功后返回 `75`；最后一块成功后返回 `20`。

如果数据块传输校验失败，BL 返回 `1f` 并结束本轮升级。原厂 `mcu_util` 会把固件文件位置退回开头，重新执行完整升级流程，而不是只重发当前数据块。最后一块不足一页时会保留该 Flash 页中未被新固件覆盖的尾部内容。

### 命令 `02`：启动应用

BL 再次验证应用 CRC。无效时返回 `1f` 并继续停留在命令循环；有效时返回 `75`，等待 1000 ms，关闭 SysTick、清除 NVIC 中断使能及挂起状态，然后从 `0x08003000` 读取 MSP 和复位入口完成交接。

## Menuconfig 配置

本工程复用相邻 Katapult 工程中的 Kconfiglib。请进入项目指定的 `T113` WSL 环境，在本目录执行：

```sh
make menuconfig
```

界面操作与 Linux 内核 menuconfig 类似：方向键移动，Enter 进入，Space 选择，左右方向键选择底部的保存或退出按钮。当前选项包括：

- **目标控制板**：C23、C13、C10 三选一。该选择同时决定 Cortex-M 架构、平台驱动、RAM 大小、Flash 容量、写入页大小和板卡标识。
- **GD32F303 Flash 容量**：仅在选择 C23/C13 时出现，默认分别为 256/128
  KiB；可为已确认的大容量兼容芯片设置到 1024 KiB。大于 512 KiB 后协议
  长度上限和底层 bank 1 路径会同时生效。
- **上电等待升级握手时间**：范围 1000～60000 ms，默认 15000 ms，对应 `CONFIG_BOOT_WAIT_MS`。
- **命令及数据包接收超时**：范围 100～5000 ms，默认 500 ms，对应 `CONFIG_PACKET_TIMEOUT_MS`。它用于命令、校验字节和升级数据的单次字节接收等待。

保存后生成 `.config`。构建时还会生成 `build/configured/autoconf.h`，源码通过其中的 `CONFIG_*` 宏取得配置。修改配置后再次运行 `make` 即会重新生成并编译相关产物。

如果尚无 `.config`，直接运行 `make` 会调用 `olddefconfig` 自动建立默认 C23 配置。也可执行：

```sh
make olddefconfig    # 补齐新增选项并保留已有选择
make distclean       # 删除构建目录和 .config
```

## 构建方法和产物

按 menuconfig 当前选择构建：

```sh
make
```

主要产物：

| 文件 | 用途 |
|---|---|
| `build/configured/bootloader.elf` | 带段信息的 ELF，供反汇编和调试 |
| `build/configured/bootloader.elf.map` | 链接映射，用于核对符号和空间占用 |
| `build/configured/bootloader.bin` | 裸 Bootloader 研究镜像 |
| `build/configured/autoconf.h` | Kconfig 生成的 C 宏 |

无需交互、一次构建全部三个原厂配置：

```sh
make profiles
```

对应输出位于 `build/c23/`、`build/c13/`、`build/c10/`。单独构建可使用 `make c23`、`make c13` 或 `make c10`。`make clean` 只删除 `build/`，保留 `.config`。

运行主机侧回归测试：

```sh
python -m pytest -q -p no:cacheprovider
make hosttest
```

测试会核对协议算法、重试限制、构建镜像布局，以及三份原厂完整备份中的 BL 哈希、向量、板号、应用版本、长度和 CRC。
`make hosttest` 会把实际 `src/protocol.c` 分别按 C23、C13、C10 三种板型编译成
主机测试程序，以模拟 UART、Flash 和应用区动态执行 12 条状态机路径：扇区查询、
有效/无效版本查询、有效/无效应用启动、正常升级、Flash 第三次重试成功、三次失败、
数据校验失败、长度越界、长度校验失败后恢复及五次失败耗尽。它直接运行待上 MCU 的 C 实现，不是用 Python 重新写一份
协议算法；测试只使用主机内存，不连接或修改任何板卡。

## 当前边界与安全要求

已经达到的是“依据三份 BL 和升级工具交叉验证、可以编译和静态审查的功能重建”，不是原厂源码恢复，也不是已经完成实机认证的替代 Bootloader。看门狗、复位原因、Flash 错误边界、断电恢复、PCB 实际 UART 走线及异常包精确时序仍需受控硬件试验。

**不要把这些研究镜像直接刷入打印机。** 必须保留完整 Flash 备份和选项字节。首次硬件试验应使用可牺牲的开发板，或在可靠连接 SWD、确认能够解除读保护并恢复整片 Flash 的条件下进行。

更细的反汇编证据、函数地址和置信度分类见 [`REVERSE_ENGINEERING_STATUS.md`](REVERSE_ENGINEERING_STATUS.md)。

## 持续集成与发布

每次 push、Pull Request 或手工触发都会在 Ubuntu GitHub Runner 上执行：

1. 安装 GNU Arm Embedded、Kconfiglib 和 pytest；
2. 生成默认 Kconfig；
3. 交叉编译 C23、C13、C10；
4. 运行三个配置的原生 C 协议状态机测试；
5. 运行 Python 协议、布局和构建回归；
6. 上传 BIN、ELF 和 MAP 作为 CI artifact。

推送形如 `v0.1.0` 的 tag 后，Release 工作流会重复全部验证，生成包含三套
BIN/ELF/MAP、文档及 `SHA256SUMS` 的压缩包，并创建标记为 prerelease 的
GitHub Release。发布产物仍然是研究镜像，不能因为通过 CI 就直接刷入生产设备。
